# Feature Specification: 极简个人博客（第一版）

**Feature Branch**: `001-personal-blog`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "开发一个极简、高性能的个人博客系统，面向两类角色：读者与作者（我自己）。读者可浏览文章列表与沉浸式详情、基础 SEO；作者用仓库内 Markdown 轻量发布；不做社交/评论/复杂 CMS/登录；标签筛选若过重可延后。"

## Clarifications

### Session 2026-07-30

- Q: 第一版里，一篇 Markdown 怎样才算「已发布」、可以对读者公开？ → A: 文章元数据里显式标记已发布（例如 `draft: false` / `published: true`）；未标记或标为草稿则不公开
- Q: 第一版首页文章列表要一次展示多少篇？ → A: 一次展示全部已发布文章（不做分页或「更早文章」截断）
- Q: 文章详情的可读网址，在两篇文章标题相同或标题变更时，应如何保证互不冲突且地址稳定？ → A: 作者在元数据中提供唯一可读短标识（slug）；网址基于该标识，不随标题改动而变
- Q: 第一版文章是否需要支持图片，以及支持到什么程度？ → A: 支持正文内 Markdown 图片展示，并支持可选封面图（列表或详情顶部展示）
- Q: 可选封面图在第一版应出现在哪些位置？ → A: 首页列表与详情页都展示封面（无封面则不占位或轻量占位）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 浏览文章列表 (Priority: P1)

作为读者，我打开博客首页后，能尽快看到已发布文章的列表（标题、摘要、日期），并点击某一篇进入详情。

**Why this priority**: 没有可读列表就没有博客的最小可用价值；也是首屏性能的主战场。

**Independent Test**: 准备至少 3 篇已发布文章后，仅打开首页即可验证列表展示与进入详情的入口；不依赖筛选、搜索或作者后台。

**Acceptance Scenarios**:

1. **Given** 站点存在至少一篇已发布文章，**When** 读者打开首页，**Then** 可见文章列表，每项至少包含标题、摘要与发布日期；若该文有封面图，则列表项同时展示封面。
2. **Given** 首页列表已展示，**When** 读者点击某篇文章，**Then** 进入对应该篇的详情阅读页。
3. **Given** 站点暂无已发布文章，**When** 读者打开首页，**Then** 看到明确的空状态说明（简体中文），而非空白或报错页。
4. **Given** 存在多篇已发布文章，**When** 读者查看列表，**Then** 文章按发布日期从新到旧排列，且首页一次列出全部已发布文章（无分页、无截断）。
5. **Given** 某已发布文章无封面图，**When** 读者查看首页列表，**Then** 该条目仍完整展示标题等信息，不因缺少封面而错误或布局崩溃。

---

### User Story 2 - 沉浸式阅读正文 (Priority: P1)

作为读者，我在文章详情页能专注阅读完整正文，页面干扰少，阅读体验干净。

**Why this priority**: 与列表同为第一版核心体验；宪章要求沉浸式阅读，优先于扩展功能。

**Independent Test**: 打开任意一篇已发布文章的详情 URL，即可验证标题、元信息与正文可读性，无需列表页以外的能力。

**Acceptance Scenarios**:

1. **Given** 某篇文章已发布，**When** 读者打开其详情页，**Then** 可见文章标题、发布日期与完整正文。
2. **Given** 读者正在阅读详情页，**When** 浏览正文区域，**Then** 页面无评论区、社交分享强制弹层、注册引导等干扰阅读的模块。
3. **Given** 文章正文包含常见 Markdown 结构（标题、段落、列表、链接、代码块、图片），**When** 读者查看详情页，**Then** 上述结构以清晰可读的形式呈现，正文内图片可正常显示。
4. **Given** 文章元数据提供了可选封面图，**When** 读者打开详情页，**Then** 在详情顶部展示该封面；未提供封面时详情版面仍完整可用。
5. **Given** 读者在详情页，**When** 需要返回列表，**Then** 存在明确、轻量的返回首页/列表方式。

---

### User Story 3 - 作者用 Markdown 发布文章 (Priority: P1)

作为作者（站点所有者），我通过在仓库中编写 Markdown 文件并完成发布流程后，文章出现在站点上，无需使用复杂内容管理后台或账号登录。

**Why this priority**: 没有可持续的发文路径，列表与详情无法长期有内容；且须保持轻量。

**Independent Test**: 新增一篇符合约定的 Markdown 文章并完成发布流程后，仅通过首页与详情页即可确认文章已上线。

**Acceptance Scenarios**:

1. **Given** 作者按约定创建一篇含必要元信息的 Markdown 文章，**When** 完成发布流程，**Then** 该文出现在首页列表中。
2. **Given** 文章已发布且元数据含唯一 slug，**When** 读者打开对应详情页，**Then** 标题、摘要（若有）、标签（若有）、发布日期与正文与源文件一致，且地址体现该 slug。
3. **Given** 作者更新已发布文章的标题但保持 slug 不变并再次发布，**When** 读者使用原详情地址访问，**Then** 仍打开同一篇文章并看到新标题。
4. **Given** 作者更新已发布文章的 Markdown 正文并再次发布，**When** 读者刷新详情页，**Then** 看到更新后的内容。
5. **Given** 作者仅完成本地写作、尚未完成发布流程，**When** 读者访问站点，**Then** 不会看到该未发布内容。
6. **Given** 某 Markdown 未显式标记为已发布（或标记为草稿），**When** 读者访问首页或尝试打开其详情，**Then** 该文不出现在公开列表，详情亦不可按已发布文章访问。
7. **Given** 某文标记为已发布但缺少 slug，**When** 完成站点更新后读者访问公开站点，**Then** 该文不出现在公开列表（视为未完成发布）。

---

### User Story 4 - 基础 SEO 可发现 (Priority: P2)

作为读者（及搜索引擎），我可以通过可读的地址访问文章，并在页面中获得正确的标题与描述，正文可被抓取索引。

**Why this priority**: 可发现性是个人博客长期价值的一部分，但可在列表与阅读可用之后立即交付。

**Independent Test**: 查看任意已发布文章详情页的地址栏与页面基础信息（标题、描述、正文是否在初始文档中可见）即可验收，不依赖分析后台。

**Acceptance Scenarios**:

1. **Given** 一篇已发布文章，**When** 查看其详情地址，**Then** 地址可读（人类可大致理解对应哪篇文章），而非无意义的纯随机串作为唯一标识。
2. **Given** 读者打开首页或详情页，**When** 查看浏览器标题，**Then** 标题能区分站点与当前页面（详情页包含文章标题）。
3. **Given** 一篇带摘要的已发布文章，**When** 查看页面描述类元信息，**Then** 描述反映该文摘要或等价说明。
4. **Given** 搜索引擎或禁用脚本的客户端访问详情页，**When** 获取页面内容，**Then** 仍能获得文章正文（正文不依赖仅客户端渲染才能出现）。

---

### User Story 5 - 按标签筛选文章 (Priority: P3)

作为读者，我希望按标签查看相关文章。

**Why this priority**: 用户说明第一版若过重可延后；不阻塞 P1 最小闭环。

**Independent Test**: 当存在带标签的多篇文章时，选择某一标签后仅看到带该标签的文章。

**Acceptance Scenarios**:

1. **Given** 多篇文章带有不同标签且本能力已交付，**When** 读者选择某一标签，**Then** 列表仅显示含该标签的已发布文章。

> 第一版范围：**不实现**本用户故事。保留于此标明延后项，避免后续误当作已承诺能力。

---

### Edge Cases

- 文章缺少摘要时：列表仍展示标题与日期，摘要位不展示或展示约定占位，不得导致页面错误。
- 文章缺少标签时：详情与列表正常展示，不显示标签区域即可。
- 两篇文章标题相同：仍可分别访问，互不覆盖；依赖作者提供的唯一可读短标识（slug），而非标题本身。
- 两篇文章 slug 冲突：后发布/冲突项 MUST NOT 静默覆盖已有公开文章；作者侧应能发现并修正（具体提示方式在方案阶段约定）。
- 文章标题变更但 slug 不变：原详情网址 MUST 仍指向同一篇文章。
- Markdown 含不支持或异常语法：页面仍可打开，尽量展示可解析部分，不得整站崩溃。
- 正文或封面图片缺失/失效：页面仍可打开；失效图不导致整页不可用，封面缺失时不留错误态阻塞阅读。
- 发布日期格式异常或缺失：即使元数据标为已发布，也不得出现在公开列表（或视为未完成发布），避免排序与展示异常。
- 元数据缺少显式「已发布」标记、或明确为草稿：一律不公开；不得仅因文件存在于仓库而对读者可见。
- 访问不存在的文章地址：返回清晰的「未找到」说明（简体中文），并提供回到首页的途径。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供首页文章列表，展示已发布文章的标题、摘要（若有）、发布日期，以及封面图（若有）；第一版 MUST 在同一首页一次展示全部已发布文章，MUST NOT 做分页或「只显示最近 N 篇」的截断。
- **FR-002**: 系统 MUST 允许读者从列表进入对应文章详情页。
- **FR-003**: 系统 MUST 在详情页展示文章标题、发布日期与完整正文，并保持沉浸式、低干扰的阅读布局；若文章有封面图，MUST 在详情页顶部展示。
- **FR-004**: 作者 MUST 能以仓库内 Markdown 文件作为文章主要内容来源进行写作与发布，且第一版 MUST NOT 依赖复杂 CMS 后台或用户注册登录。
- **FR-005**: 每篇文章 MUST 支持基本元信息：标题、正文、摘要、标签、发布日期、可选封面图；摘要、标签与封面图允许为空。
- **FR-005a**: 系统 MUST 支持正文内 Markdown 图片的展示；若提供封面图，MUST 同时在首页列表项与详情页顶部展示；无封面时 MUST NOT 阻塞列表或阅读，可采用不占位或轻量占位。
- **FR-005b**: 文章配图（封面与正文图）的文件来源 MUST 可随仓库版本管理；页面示意/设计稿仍以 `docs/ui/` 为准，与文章配图目录区分。
- **FR-006**: 仅「已发布」文章 MUST 对读者可见；未完成发布流程的内容 MUST NOT 出现在公开列表或详情中。一篇文章是否已发布 MUST 由其元数据中的显式发布标记决定（例如标记为已发布 / 非草稿）；未标记或标为草稿的 MUST NOT 公开。
- **FR-007**: 公开页面文案 MUST 使用简体中文。
- **FR-008**: 系统 MUST 为首页与文章详情提供可读 URL，以及合适的页面标题与描述类信息。文章详情 URL MUST 基于作者在元数据中提供的唯一可读短标识（slug）；slug MUST 在已发布文章中唯一；标题变更 MUST NOT 改变既有详情 URL。
- **FR-008a**: 已发布文章 MUST 包含可用的 slug；缺少 slug 的文章 MUST NOT 作为已发布内容对读者公开（或视为未完成发布）。
- **FR-009**: 文章正文 MUST 在不依赖客户端脚本执行的前提下对抓取方可读（可被索引的正文）。
- **FR-010**: 第一版 MUST NOT 提供评论、社交互动、用户注册/登录、复杂内容管理后台。
- **FR-011**: 第一版 MUST NOT 提供按标签/分类筛选（见 User Story 5，延后）。
- **FR-012**: 页面视觉与示意图片若已提供，规格与实现引用 MUST 以 `docs/ui/` 下对应文件为准；若尚未放入设计稿，布局 MUST 仍满足沉浸阅读与低干扰约束。
- **FR-013**: 应用代码布局 MUST 遵循项目约定：前端位于 `apps/frontEnd/`，后端位于 `apps/backEnd/`（本条为仓库约束，不规定具体技术选型）。

### Key Entities

- **文章（Post）**: 一篇博客内容；属性包括标题、正文、摘要（可选）、标签（可选，可多个）、发布日期、显式发布标记（已发布/草稿或未标记）、唯一可读短标识 slug（必填方可公开）、封面图（可选）。正文可包含 Markdown 图片。公开可见性以显式发布标记为准；公开访问地址以 slug 为准，不以标题生成或随标题变更。
- **标签（Tag）**: 文章的主题标记；第一版仅作为文章元信息存储与展示（若有），不提供筛选交互。
- **作者（Author）**: 站点所有者；第一版不建模为可登录用户，仅表示内容由仓库维护者发布。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 作者按约定发布后，读者能在公开站点看到至少 3 篇示例文章的列表与详情；当已发布文章超过 3 篇时，首页仍须一次展示全部已发布文章。
- **SC-002**: 在常规宽带网络与常规个人设备上，读者打开首页后，**1 秒内**能看到文章列表的主要内容（标题等），体感上达到「明显快」的首屏；有封面图时仍须满足该观感目标（可通过合理的图片策略达成，具体方案阶段确定）。
- **SC-007**: 对带封面与不带封面的已发布文章，列表与详情均能正确展示或优雅省略封面，且正文内 Markdown 图片在详情中可见。
- **SC-003**: 读者从打开首页到开始阅读某篇文章正文，主路径（首页 → 点击 → 详情）可在 **10 秒内**完成（不含阅读正文本身）。
- **SC-004**: 任意已发布文章详情页具备基于 slug 的可读 URL，浏览器标题包含文章标题，且禁用脚本时仍可获取正文要点；修改标题后原 URL 仍可打开同一篇文章。
- **SC-005**: 详情页在第一版验收中不含评论、登录墙或社交强制模块；受访读者可完成一次不受打断的阅读。
- **SC-006**: 作者从完成一篇合格 Markdown 到公开发布，无需注册/登录后台账号，发布步骤保持轻量（可文档化的短流程）。

## Assumptions

- 第一版受众为个人站点：单一作者，读者匿名访问即可。
- 「发布」指：作者在 Markdown 元数据中将文章显式标记为已发布，并完成约定的内容入库与站点更新流程（例如提交仓库并完成部署/构建）；具体工具链在方案阶段确定，本规格不绑定实现技术。
- 显式发布标记的具体字段名在方案阶段约定即可，但语义必须区分「已发布」与「草稿/未标记」。
- 标签/分类筛选明确延后到后续版本；第一版标签若存在仅用于展示。
- 「毫秒级首屏」在本规格中落为可验证的用户侧目标：首页主要内容 1 秒内可见；更细的实验室指标在方案/任务中细化，但不得与该用户目标冲突。
- 设计稿将逐步放入 `docs/ui/pages/`（如 `home`、`article-detail`）；在缺失前，以宪章的沉浸阅读与反干扰原则约束版面。
- 第一版首页不做分页；文章量按个人博客常见规模（数十篇量级）理解。若未来文章极多导致体验或性能明显下降，另开规格处理，不在本版范围内预做复杂列表策略。
- 移动端与桌面端均需可阅读；不要求第一版提供独立 App。
- 不包含多语言切换；站点语言为简体中文。
