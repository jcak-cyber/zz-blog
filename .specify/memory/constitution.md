# zz-blog 宪章

## Core Principles

### I. 中文优先 (Chinese-First)

项目后续所有文档以及开发过程中的描述，MUST 以简体中文为基本语言。
适用范围包括但不限于：功能规格（spec）、技术方案（plan）、任务清单（tasks）、
检查清单（checklist）、宪章修订说明、提交说明、PR 描述、评审意见、
以及 Agent/开发协作中面向人的过程说明。

代码标识符（变量名、函数名、类型名、文件路径等）MAY 使用英文，以符合
通用工程惯例；但面向人阅读的注释、文档字符串、用户可见文案、以及上述
过程文档 MUST 使用简体中文。若需引用英文专有名词、协议名或 API 名称，
MUST 在中文语境中保留原文，必要时附简短中文说明。

**理由**：统一沟通语言，降低协作与评审成本，避免中英混杂导致规格歧义。

### II. 规格驱动 (Spec-Driven)

新功能 MUST 先形成可评审的规格，再进入方案设计、任务拆解与实现。
未经规格（或等价书面约定）批准的实现变更，MUST NOT 作为默认交付路径。
规格、方案与任务之间出现冲突时，MUST 先修订上游文档再继续编码。

**理由**：本项目以 Spec Kit 为协作骨架，规格是唯一可信的需求真相来源。

### III. 简洁优先 (Simplicity First)

默认选择更简单、更少概念的方案。新增抽象、依赖、功能或基础设施前，MUST
说明其如何直接服务「写作」或「阅读」；无法说明则 MUST NOT 引入。
禁止为「将来可能用到」而提前设计（YAGNI）。MUST NOT 以功能数量或
平台化能力作为成功标准；核心目标是极简、易维护，而非功能堆砌。

**理由**：个人博客的价值在写作与阅读体验，多余功能会侵蚀性能与可维护性。

### IV. 可验证交付 (Verifiable Delivery)

每个用户故事与任务 MUST 带有可独立验证的验收条件（Given/When/Then
或等价检查项）。实现完成的判定以验收条件通过为准，不以「代码已提交」
作为完成标准。涉及性能与 SEO 的需求，MUST 附带可度量的验收指标。

**理由**：可测试的验收条件是规格质量与交付质量的共同底线。

### V. 一致性 (Consistency)

命名、目录结构、文档模板与交互模式 MUST 与已有约定保持一致。
应用源代码 MUST 放在统一代码根目录下，并按前端 / 后端分目录存放
（见「仓库目录布局」）。若需偏离现有模式，MUST 在方案或任务中写明理由，
并同步更新相关约定文档。

**理由**：一致性降低认知负担，便于后续功能按同一节奏扩展。

### VI. 性能优先 (Performance First)

首屏加载 MUST 以毫秒级体验为目标进行设计与验收；任何会显著拖慢首屏、
阻塞渲染或无必要增大客户端载荷的方案，MUST NOT 作为默认选择。
新增交互或第三方脚本前，MUST 评估对首屏与阅读流畅度的影响；若影响
不可接受，MUST 拒绝或改为可选/延迟加载。

**理由**：毫秒级首屏与沉浸式阅读是本系统相对「功能堆砌型博客」的核心差异。

### VII. 内容与可发现性 (Content & Discoverability)

发布新文章 MUST 以 Markdown 为主要作者工作流，流程 MUST 保持轻量、
可本地编辑、易于维护。系统 MUST 具备良好的 SEO 基础能力（可读 URL、
合理标题层级、元信息、可被索引的正文 HTML 等），且这些能力 MUST NOT
以牺牲首屏性能或阅读沉浸感为代价。

**理由**：写作门槛低、搜索可达，是个人博客可持续产出与被发现的前提。

## 产品定位

zz-blog 是极简、高性能、专注写作体验的个人博客系统。

- **要做什么**：毫秒级首屏、沉浸式阅读、Markdown 轻松发文、良好 SEO、易维护。
- **不做什么**：不以功能堆砌、社交化、复杂后台或平台化扩展为默认方向。
- **成功标准**：写作流畅、阅读沉浸、首屏足够快、维护成本足够低。

凡与上述定位冲突的需求，MUST 在规格阶段显式降级、推迟或拒绝。

## 仓库目录布局

应用代码 MUST 统一放在仓库根目录下的 `apps/` 中，不得散落在根目录或其他
随意路径：

```text
apps/
  frontEnd/   # 前端应用代码
  backEnd/    # 后端应用代码
docs/
  ui/         # 页面相关图片的唯一本地来源
    pages/    # 按页面存放（如 home、article-detail）
    shared/   # 跨页共用图（图标、装饰等）
```

- 前端相关源码、前端依赖清单与前端构建配置 MUST 位于 `apps/frontEnd/`。
- 后端相关源码、后端依赖清单与后端运行配置 MUST 位于 `apps/backEnd/`。
- 页面设计稿、页面示意与页面所需静态图片 MUST 统一放在 `docs/ui/`：
  - 某页面专用图 → `docs/ui/pages/<页面名>/`
  - 多页共用图 → `docs/ui/shared/`
  - 规格、方案、实现与评审引用页面图片时，MUST 使用上述路径，
    MUST NOT 再另建平行图片目录或仅存在于聊天附件中作为唯一来源。
- Spec Kit 元数据（`.specify/`）、Cursor 技能（`.cursor/`）等协作脚手架
  MUST NOT 放入 `apps/`；它们继续留在仓库根目录。
- 共享类型、脚本或文档若确需跨端复用，MUST 先在方案中论证，再新增明确命名的
  目录；默认 MUST NOT 在根目录直接堆放应用代码。

## 语言与文档约束

- 所有 Spec Kit 产物（spec / plan / tasks / checklist / analyze 报告等）
  MUST 使用简体中文撰写标题与正文。
- 模板中的固定英文结构标题（如 `Core Principles`、`Governance`）MAY 保留；
  其下内容 MUST 使用简体中文。
- 对外用户界面文案默认简体中文；若支持多语言，MUST 以中文为源语言，
  再派生其他语言。
- 技术术语首次出现时，SHOULD 采用「中文（English）」形式，其后可只用中文
  或约定缩写。

## 体验与质量约束

- 阅读页 MUST 优先保障正文可读性与沉浸感：减少干扰性导航、弹层与动效噪音。
- 性能相关变更 MUST 在方案或任务中写明预期影响与验证方式（如 Lighthouse、
  Web Vitals、本地计时等约定指标）。
- SEO 相关输出 MUST 可由静态或服务端渲染的文档结构验证，而非仅依赖客户端脚本。
- 文章内容源 MUST 可版本管理（例如仓库内 Markdown 文件），避免不可移植的专有存储
  作为唯一真相来源。

## 开发工作流

1. 宪章合规：新增或变更功能前，确认不违背本宪章原则与产品定位。
2. 规格先行：使用 specify →（按需 clarify）→ plan → tasks → implement。
3. 评审门禁：规格与方案在进入下一阶段前 MUST 可被人工审阅；评审 MUST 检查
   是否偏离「极简 / 性能 / 写作与阅读体验」。
4. 一致性检查：任务生成后 SHOULD 运行 analyze，消除跨文档矛盾。
5. 交付验收：实现以任务验收条件为准；未完成项通过 converge 补齐。

## Governance

本宪章优先于口头约定与临时习惯。修订流程如下：

1. 提出修订：说明变更动机、影响范围与迁移方式。
2. 版本号：
   - MAJOR：删除或重新定义既有原则，导致既有实践不兼容。
   - MINOR：新增原则/章节，或实质性扩展既有指导。
   - PATCH：措辞澄清、错别字与非语义润色。
3. 生效：更新 `constitution.md`，同步修订页头 Sync Impact Report，
   并更新 Version / Last Amended 日期（ISO `YYYY-MM-DD`）。
4. 合规：PR 与规格评审 MUST 核对是否符合本宪章；涉及新功能或新依赖时，
   MUST 同时证明未损害性能、简洁性与写作/阅读体验。
